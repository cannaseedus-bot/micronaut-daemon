# WebGL2 Trainer

## Architecture

`tools/dashboard/webgl2-trainer-dashboard.ps1` hosts the browser runtime in WPF WebView2. It loads the local WebView2 Core and WPF assemblies plus `WebView2Loader.dll` from `.CSS-C/webview2_sdk`, then maps `.CSS-C` to `https://cssml.local`. The virtual HTTPS origin lets the page load local modules and shader resources consistently. Keep bridge messages small: send status, loss, step counts, and checkpoint metadata rather than tensor arrays. Compiled tools and trainer binaries belong in `tools/bin`; source, scripts, tests, and build definitions are organized under `tools/src`, `tools/scripts`, `tools/test`, and the relevant build folders.

## Available Training Paths

- **CSS-ML demo:** `.CSS-C/demo/gsnr-universe.html` loads `.CSS-C/css-ml-runtime/src/runner/webgl2-model-trainer.js`. The graph uses synthetic MNIST-shaped data. WebGL2 executes GEMM, linear, ReLU, SiLU, and elementwise multiply kernels; graph backpropagation and AdamW currently use the CPU reference. Select **CSS-ML / WebGL2 model trainer**, then press **TRAIN MODEL** in the embedded page. This does not train Gemma or another language model.
- **PyTorch/OpenCL Gemma 3 300M:** select this mode to run `tools/train_gemma3_scratch.py` from the 303,995,904-parameter baseline in `build/gemma3-reasoning-opencl-300m-24h`. Forward/backward are CPU-side; OpenCL performs AdamW updates. Periodic full-state checkpoints support resume. The selected token bin, baseline, tokenizer, output path, and duration must be valid.
- **Large Safetensors sweep:** the **WEBGL2 LARGE MODEL SWEEP** button invokes `tools/trainer-dashboard/kuhul-es/bin/kuhul-es.js train-webgl2-sweep`. Its child wrapper exists at `tools/trainer-dashboard/kuhul-es/runtime/src/webgl2_hf_safetensor_trainer.cjs`, but delegates to an implementation missing from this checkout, so the sweep cannot currently finish a training run. It is separate from the CSS-ML demo and the bounded kernel parity results below.

## Gemma Graph Builder Boundary

`tools/dashboard/gemma-graph.mjs` now validates Gemma 3 text config and per-layer Safetensors shapes, then emits a forward DAG for one decoder layer or a contiguous layer slice. It uses the configured layer type to select sliding versus full causal attention, separate sliding/full RoPE cache inputs, centered RMSNorm, query scaling, and the checkpoint's GELU-tanh gated MLP (`GELU(gate) * up`). `bindGemmaGraphInputs` checks shapes and requires caller-provided CPU data or live resident tensors before the graph is passed to `WebGL2Executor.executeGraph`.

This is graph construction only. The caller must load configuration/header metadata and tensor payloads, tokenize and batch data, produce the correctly theta-specific RoPE tables, schedule optimizer updates, preserve/release checkpoint state, and write checkpoints. A selected upper-layer slice expects hidden states from the preceding frozen layers; this builder does not run those layers on its own. The builder is forward-only and does not yet encode backward gradients, vocabulary chunk iteration, optimizer steps, activation checkpointing, or dashboard telemetry. Kernel parity does not establish parity of a graph until this emitted graph itself is run against the matching reference model and weights.

Architecture note: this repository checkpoint config specifies `hidden_activation: gelu_pytorch_tanh` and includes `pre_feedforward_layernorm` plus `post_feedforward_layernorm`. Do not substitute the more common SiLU SwiGLU block when building its graph. The graph module fails fast on unsupported activation, bidirectional attention, or attention softcapping configurations.

The GELU-tanh GPU op (`activation_gelu_tanh`) and its backward op are registered in `webgl2.js`; CPU equivalents are registered in `cpu.js`. The opcode name is `activation_gelu_tanh` rather than `gelu_tanh`. At inputs `[-100,-20,-10,-5,-2,-1,-0.1,0,0.1,1,2,5,10,20,100]`, the GPU forward result was finite and matched `torch.nn.functional.gelu(..., approximate="tanh")` with max absolute error `4.77e-7`; upstream-gradient parity was `8.65e-7` max error. Both GPU ops ran on ANGLE / Intel HD 4600 D3D11. CPU forward error on the same values was below `7e-8`.

A generated two-layer graph (Layer 0 sliding attention, Layer 1 full causal attention, plus final norm) ran 45 nodes on the Intel HD 4600 at sequence length 45. Against a deterministic PyTorch CPU reference using the actual checkpoint tensors and the Gemma 3 decoder equations, max absolute error was `4.65e-6` and RMSE `7.55e-7`. The scheduler reported 45 WebGL2 nodes, zero CPU nodes, zero intermediate readbacks, and `20,256,768` peak resident bytes. This verifies forward graph wiring for two layers; it does not verify backward construction, token embeddings, language-model loss, weight updates, or checkpoint writing.

## WebGL2 Components and Limits

`tools/trainer-dashboard/webgl2-hf-loader.mjs` loads Safetensors into WebGL2 textures; `webgl2-tensor.mjs` manages float tensor storage; `webgl2-glyph-dispatcher.mjs` dispatches registered opcodes. The loader supports range-based rank-2 row reads (`openSafetensors`, `readTensorRows`, `loadTensorRows`, `iterateTensorRows`) so large matrices can be streamed in texture-sized strips. The source must honor HTTP byte ranges with status 206; the loader rejects a full-file response rather than silently buffering the entire checkpoint for every strip. These are primitives, not a complete optimizer, transformer trainer, or checkpoint writer.

`WebGL2Executor` exposes `createTensor`, `dispatchResident`, `readTensor`, and `releaseTensor`. Resident outputs retain their texture/FBO for later kernels; input/output aliasing is rejected to enforce ping-pong use. Released transient textures and FBOs can be reused from a dimension-keyed pool. `linear_forward_transposed` consumes checkpoint-style `[out_features,in_features]` weights, and `activation_gelu_tanh` implements Gemma 3's configured `gelu_pytorch_tanh`. Existing `dispatch` remains compatible and reads each result back for CPU consumers.

## CPU/GPU Work Placement

`executeGraph({ inputs, nodes, outputs })` runs a dependency graph with per-node `device: 'cpu' | 'webgl2' | 'auto'` placement. Inputs use `{ input: name }` references; dependencies use `{ node: id }`; nodes declare `op`, `outputDims`, and optional `params`. `auto` currently selects WebGL2 when that operation has a shader, otherwise CPU when a CPU kernel is registered. This is capability-based selection, not a learned performance policy.

The graph runner transfers CPU tensors to R32F textures only when a WebGL2 node needs them, and reads resident results back only when a CPU node needs them. It releases graph-owned intermediates after their final consumer and reuses their textures from the pool; named graph outputs remain resident until `release()` is called. Telemetry reports per-node elapsed time, backend counts, transfer counts and bytes, and peak graph-owned resident bytes. Ready WebGL2 nodes are submitted before independent CPU nodes so queued GPU work can proceed while the host executes CPU kernels. CPU work also covers safetensors I/O, tokenization/input preparation, RoPE cache construction, validation, and checkpoints. Use transfer and timing metrics to identify whether CPU/GPU boundaries are worth their cost. Placement is currently node-level; kernels are not split across CPU and GPU.

## K'UHUL, KAST/KXML, and Tensor Training

`tools/trainer-dashboard/kuhul-es/compiler/src/parser.js` uses the TypeScript Compiler API to parse KUHUL source and lower bindings, glyph calls, functions, and directives into KAST/1 graph JSON. `parser.ts` delegates to that CommonJS implementation, and the CLI's `compile` command imports `parser.js` directly; the package's `npm run build` does not compile these TypeScript wrappers. KAST is the graph/AST representation. KXML uses graph manifests and bot operations as an early vector-enabled bot framework: the unified runtime has an embed/retrieve/transform/classify/generate/tool DAG, while `runtime/src/kxml_driver.js` contains numeric embedding, normalization, matrix, and attention operations over tensor weights. Together they are a distinct bot/model path, separate from the Gemma CSS-ML WebGL2 executor.

Implementation maturity varies by path: the simple `KxmlEngine` embed/retrieve methods in `runtime/src/unified.js` currently return placeholder embeddings and randomized retrieval scores, while `kxml_driver.js` contains actual tensor math. Do not treat the placeholder adapter as proof of real vector retrieval; measure the driver and configured storage path that a bot actually invokes. Separately, `runtime/src/trainer.js` defines a small `GLSLTrainer` with trainable arrays and gradient/update steps, exporting a KAST-like structural manifest with weight artifact references. Its optional advisor in `runtime/src/trainer_semantic.js` can adjust learning rate and physics parameters from graph/metric patterns. Unit tests cover advice generation and integration, but not improved task quality or loss. Compare fixed-seed runs with the advisor enabled and disabled on the same train/holdout split to establish benefit. Extending the KAST/KXML bot model requires tensor-slice training only for the numeric weights intended to learn; it does not require copying Gemma's full tensor set unless Gemma itself is the target.

The repository also has a distinct native D3D11 path: `tools/shaders/gpt2_*.hlsl` contains GPT-2 forward/backward and Adam compute kernels, while `.CSS-C/native/lowered/cssc_gemm-matmul.hlsl` is the lowered CSS-C GEMM probe. `tools/build-cssc-gemm.ps1` compiles its runner; the resulting probe checks D3D11 GEMM against a CPU reference and does not train the WebGL2 model. `tools/build-fixed/` contains generated build output, not shader source of truth.

## AdamW Update Kernel Parity

`adamw_step` is available in the WebGL2 executor and CPU fallback. Each invocation consumes matching `weight`, `grad`, `m`, and `v` tensors and emits one selected result (`output_kind: "weight" | "m" | "v"`). This single-render-target design lets `executeGraph` chain the three outputs for each step without CPU transfers. Pass `bc1 = 1 - beta1^step` and `bc2 = 1 - beta2^step`; the weight path applies decoupled decay before the bias-corrected Adam update.

A WebView2 parity run chained five updates over an odd-sized 257-element tensor with changing gradients and non-default `lr=0.003`, `beta1=0.87`, `beta2=0.992`, `eps=2e-7`, and `weight_decay=0.035`. All per-step weight and moment outputs were compared to `torch.optim.AdamW`. GPU max absolute error stayed below `1.79e-7` for weights, `1.49e-8` for first moments, and `1.22e-8` for second moments. CPU fallback maxima were `2.39e-7`, `1.49e-8`, and `9.32e-10`, respectively. All 15 GPU nodes used the Intel HD 4600 D3D11 adapter with zero CPU nodes or scheduler readbacks; peak live memory was 16,448 bytes. This validates the isolated update math and persistent moment chaining. The existing `TrainingLoop` still calls the older dispatcher optimizer path; end-to-end training-loop placement, checkpointed optimizer state, gradient accumulation, and convergence are not yet validated.

## Closed-Loop Layer-0 Training Parity

GPU `mse_loss_rows`, `mse_loss_mean`, and `mse_loss_backward` kernels provide a resident mean-squared-error objective. `executeGraph` now accepts `result.release([outputNames])`: it releases graph intermediates while returning selected live GPU outputs to the caller, which can carry updated weights and Adam moments into the next step and explicitly release the previous state.

A three-step sequence-length-45 closed loop used all 13 checkpoint Layer-0 tensors (8,555,648 parameters), fixed synthetic hidden states and target, causal window 32, and AdamW (`lr=1e-5`, `beta1=.9`, `beta2=.999`, `eps=1e-8`, `weight_decay=.01`). Each step ran 104 forward, loss, backward, and update nodes. All 312 node executions used the Intel HD 4600 D3D11 adapter; CPU fallbacks and scheduler readbacks were zero. The resident loss fell monotonically: `3.27085638`, `3.24100828`, `3.21019387`; PyTorch losses were `3.27085638`, `3.24100924`, `3.21019554` (largest per-step difference `1.67e-6`). After step three, all updated weights and both moment tensors were compared to PyTorch: maximum absolute errors were `2.82e-6` for weights, `1.98e-8` for first moments, and `2.76e-11` for second moments. The graph-owned live peak was `106,298,884` bytes (101.37 MiB); caller-owned current W/m/v state was `102,667,776` bytes (97.91 MiB). The reusable texture pool stabilized at `129,527,832` bytes (123.53 MiB). Graph live-byte telemetry excludes caller-owned resident inputs and pooled-but-idle texture allocations, so read these memory figures separately rather than as one total.

This verifies a bounded synthetic Layer-0 optimization loop, including loss decrease and persistent GPU W/m/v state. It does not yet connect token IDs, the vocabulary head, or the dashboard's `TrainingLoop`; it is not evidence of language-model quality or long-run convergence.

## Chunked Vocabulary Operations

The CSS-ML runtime provides `embedding_lookup_chunk`, `embedding_scatter_add`, `cross_entropy_chunk_stats`, `cross_entropy_merge_stats`, `cross_entropy_loss_from_stats`, `cross_entropy_chunk_backward`, and `reduce_mean` on WebGL2 and its CPU reference. They support row-strip lookup, online stable log-sum-exp across vocabulary chunks, and per-chunk softmax-minus-target gradients without allocating `[sequence,vocabulary]` logits. `ignore_index` rows contribute neither loss nor gradient; callers pass the count of non-ignored targets for normalization. Use `sqrt(hidden_size)` for Gemma token embedding scaling. Because the checkpoint ties `lm_head.weight` to `model.embed_tokens.weight`, combine the output-head dW and embedding scatter gradient for each strip; the lookup-path gradient must include the same embedding scale.

WebView2 parity passed on the Intel HD 4600 (ANGLE/D3D11) against PyTorch 2.15 autograd with `vocab=45`, `hidden=7`, `sequence=13`, and uneven chunks `16,16,13`. It covered targets across all chunks, one `ignore_index=-100` position, scaled embedding lookup, chunked lm_head, loss, dHidden, and tied embedding-plus-head dW. Maximum absolute errors were `0` for embedding output, `1.86e-9` for logits, `2.38e-7` for loss, `6.98e-10` for dHidden, and `3.73e-9` for tied dW; the ignored-token gradient and WebGL error were both zero.

The Safetensors row reader also passed an in-memory F16 fixture: it requested prefix bytes `[0,8)`, the 64-byte header `[8,72)`, and the selected row `[76,80)`, decoding exactly to `[2,-4]`. A WebView2 virtual-host mapping probe against a 4 KiB local fixture returned `206 Partial Content`, `Accept-Ranges: bytes`, `Content-Range: bytes 100-199/4096`, and exactly 100 bytes for `Range: bytes=100-199`. This verifies the dashboard's mapped-folder delivery path; the real 1.2 GB checkpoint has not yet been streamed end to end. The current full-file `loadSafetensors` API still reads the entire file; use the row-slice API for the oversized tied matrix. These parity checks do not yet compose a full Gemma vocabulary training graph, load/tokenize the real corpus, add tiled optimizer state, write Safetensors checkpoints, or connect the dashboard trainer loop.

Do not label a run GPU-trained unless its required forward and update operations execute on the GPU. Keep the 300M CPU/OpenCL preset within the 10 GiB memory guard; full-precision Adam training at 900M–1.2B parameters exceeds that budget before runtime overhead.
